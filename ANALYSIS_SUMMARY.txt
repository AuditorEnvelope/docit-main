🔄 COMPLETE DATA FLOW
═══════════════════════════════════════════════════════════════════════════════

FLOW 1: Organization Onboarding
  1. User logs in with GitHub
     └─ OAuth callback → create user in `users` table
     └─ Store token in `user_github_tokens` table
     └─ Create session in `sessions` table

  2. User registers organization
     └─ Frontend: POST /webhook/register {org_id}
     └─ Backend: Store in `org_registrations` table
     └─ Backend: Store in `org_webhooks` table with token

  3. User installs GitHub App
     └─ GitHub sends webhook
     └─ Backend: Store in `github_installations` table

FLOW 2: Code Push & Documentation Generation
  1. Developer pushes code
     └─ GitHub sends webhook to POST /webhook

  2. Webhook Handler (webhook_multi_org.py)
     └─ Verify webhook signature
     └─ Extract org from repo name
     └─ Look up user from `org_registrations` table
     └─ Get user's GitHub token
     └─ Create CommitEvent object
     └─ Store in `commit_events` table
     └─ Return 200 OK immediately

  3. Event Consumer (event_consumer.py)
     └─ Poll `commit_events` table every 5 seconds
     └─ Find unprocessed events
     └─ Get user's GitHub token from `user_github_tokens`
     └─ Clone repository
     └─ Analyze code
     └─ Generate docs (LLM: Gemini → Groq → DeepSeek)
     └─ Commit docs to GitHub
     └─ Store in `doc_versions` table
     └─ Update `repo_sync_state` with latest SHA
     └─ Mark event as processed

🔑 KEY INSIGHTS
═══════════════════════════════════════════════════════════════════════════════

1. MULTI-ORG SUPPORT
   → Each user can have multiple organizations
   → Each org has its own GitHub token
   → org_registrations table maps user → org
   → org_webhooks table maps org → token

2. WEBHOOK FLOW
   → GitHub sends webhook to /webhook endpoint
   → Webhook handler extracts org from repo name
   → Looks up user from org_registrations table
   → Attaches user context to event
   → Event stored in commit_events table
   → Returns 200 OK immediately (async processing)

3. EVENT CONSUMER
   → Polls commit_events table every 5 seconds
   → Processes up to 3 events concurrently
   → Gets user's GitHub token from user_github_tokens
   → Clones repo using token
   → Generates docs using LLM
   → Commits docs back to GitHub
   → Updates repo_sync_state for next startup

4. OPTIMIZATION
   → repo_sync_state table stores last processed SHA
   → On startup, only fetches commits since last SHA
   → Speeds up recovery from downtime
   → Avoids re-processing old commits

5. SECURITY ISSUES
   → GitHub tokens stored in plaintext
   → JWT tokens stored in plaintext
   → Should use encryption (Fernet)
   → Should hash tokens before storing
