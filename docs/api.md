## 1. Introduction

Pustak is a new, dedicated documentation platform designed to host and render documentation generated by the `lekhak_ai` (DocAI) system. This API provides the interface for `lekhak_ai` (via `pustak_integration.py`) and potentially other systems to publish, update, and manage documentation content within Pustak.

The primary goal of these APIs is to:
*   Enable automated publishing of documentation generated by DocAI.
*   Provide a mechanism for Pustak to react to external events and triggers.

## 2. Authentication

All Pustak API endpoints require authentication using an API Key. This key must be securely generated and configured on both the Pustak platform and the consuming system (e.g., `lekhak_ai`'s `pustak_integration.py` script).

### Authentication Method: API Key

The API Key must be sent in the `X-API-Key` HTTP header for every request.

**Header Example:**
```
X-API-Key: your_super_secret_pustak_api_key
```

### How to Obtain/Configure an API Key:
(This would typically be done via Pustak's administration interface or environment configuration.)

*   **For Development/Testing:** Keys can be configured as environment variables (e.g., `PUSTAK_API_KEY`) within the Pustak application.
*   **For Production:** Securely generate a strong API key and configure it in Pustak's environment (e.g., Vercel environment variables if deployed there) and provide it to the `pustak_integration.py` script as a secret.

**Security Considerations:**
*   Always transmit API keys over HTTPS.
*   Do not hardcode API keys directly into client applications or public repositories.
*   Rotate API keys periodically.

## 3. Error Handling

The Pustak API uses standard HTTP status codes to indicate the success or failure of an API request. In case of an error, the API will return a JSON object with details about the error.

**Standard Error Response Format:**
```json
{
  "status": "error",
  "code": "string",       // A unique, internal error code (e.g., "INVALID_API_KEY", "VALIDATION_ERROR")
  "message": "string",    // A human-readable message describing the error
  "details": "object"     // (Optional) More specific details, e.g., validation errors for specific fields
}
```

**Common HTTP Status Codes:**

| Status Code | Description                                   | Error Code Examples        |
| :---------- | :-------------------------------------------- | :------------------------- |
| `200 OK`    | Request successful.                           | -                          |
| `201 Created` | Resource created successfully.                | -                          |
| `400 Bad Request` | The request was malformed or invalid.     | `VALIDATION_ERROR`, `MALFORMED_JSON` |
| `401 Unauthorized` | Authentication failed (missing/invalid API Key). | `INVALID_API_KEY`, `MISSING_API_KEY` |
| `403 Forbidden` | The authenticated user does not have permission to access the resource. | `PERMISSION_DENIED` |
| `404 Not Found` | The requested resource was not found.     | `ENDPOINT_NOT_FOUND`       |
| `405 Method Not Allowed` | The HTTP method used is not supported for this endpoint. | `METHOD_NOT_ALLOWED`       |
| `429 Too Many Requests` | Rate limit exceeded. (To be implemented) | `RATE_LIMIT_EXCEEDED`      |
| `500 Internal Server Error` | An unexpected error occurred on the server. | `SERVER_ERROR`, `INTEGRATION_FAILED` |

## 4. API Endpoints

### POST /api/sync

This endpoint is used by the `lekhak_ai` system (via `pustak_integration.py`) to synchronize documentation content for a specific repository and document type within Pustak. It allows publishing new documents or updating existing ones.

*   **Purpose:** Ingest or update a collection of documentation pages.
*   **Method:** `POST`
*   **URL:** `https://pustak.example.com/api/sync`

#### Request

**Headers:**
*   `Content-Type: application/json`
*   `X-API-Key: your_super_secret_pustak_api_key`

**Body (JSON):**

The request body should contain the `repoName`, `docType`, an optional `version`, and an array of `documents` to be synchronized. Existing documents with the same `repoName`, `docType`, and `id` will be updated; new documents will be created.

```json
{
  "repoName": "string",        // REQUIRED. The name of the repository (e.g., "my-ai-project").
                               // This forms part of the URL structure: /repo/[repoName]/...
  "docType": "string",         // REQUIRED. The type of documentation (e.g., "feature-docs", "api-ref", "user-guide").
                               // This forms part of the URL structure: /repo/[repoName]/[docType]/...
  "version": "string",         // OPTIONAL. The version of the documentation (e.g., "v1.0.0", "latest", "main").
                               // If not provided, Pustak may default to "latest" or inferred from git.
  "documents": [               // REQUIRED. An array of documentation pages.
    {
      "id": "string",          // REQUIRED. A unique identifier for this specific documentation page within its repo/docType/version.
                               // This can be a file path, a slug, or a UUID.
      "title": "string",       // REQUIRED. The title of the documentation page.
      "slug": "string",        // REQUIRED. A URL-friendly identifier for the page (e.g., "getting-started", "api-overview").
                               // This will be used in Pustak's routes: /repo/[repoName]/[docType]/[slug]
      "markdownContent": "string", // REQUIRED. The full content of the documentation page in Markdown format.
      "lastModified": "ISO 8601 datetime", // REQUIRED. The last modification timestamp (e.g., "2023-10-27T10:00:00Z").
      "status": "string",      // OPTIONAL. The publishing status (e.g., "published", "draft", "archived"). Default: "published".
      "metadata": {            // OPTIONAL. Additional metadata for the document.
        "author": "string",
        "tags": ["string"],    // e.g., ["installation", "setup", "quickstart"]
        "description": "string", // Short description for search/SEO
        "relatedLinks": [
          {
            "title": "string",
            "url": "string"
          }
        ],
        "customField": "any"
      }
    }
    // ... more document objects
  ]
}
```

#### Response

**Success (HTTP 200 OK):**
```json
{
  "status": "success",
  "message": "Documentation synchronized successfully.",
  "processedCount": 2, // Number of documents processed (created/updated)
  "repoName": "my-ai-project",
  "docType": "feature-docs",
  "version": "v1.0.0",
  "documentIds": ["getting-started", "advanced-usage"] // IDs of documents that were synchronized
}
```

**Error (HTTP 400 Bad Request):**
```json
{
  "status": "error",
  "code": "VALIDATION_ERROR",
  "message": "Invalid request payload.",
  "details": {
    "documents[0].title": "Title is required.",
    "repoName": "Repository name cannot be empty."
  }
}
```

#### Usage Example (cURL)

```bash
curl -X POST "https://pustak.example.com/api/sync" \
     -H "Content-Type: application/json" \
     -H "X-API-Key: your_super_secret_pustak_api_key" \
     -d '{
       "repoName": "lekhak-ai-core",
       "docType": "api-reference",
       "version": "v2.1",
       "documents": [
         {
           "id": "intro_to_api",
           "title": "Introduction to Lekhak AI API",
           "slug": "introduction-api",
           "markdownContent": "# Introduction\nThis document provides an overview of the Lekhak AI API...",
           "lastModified": "2023-10-27T10:00:00Z",
           "status": "published",
           "metadata": {
             "author": "DocAI System",
             "tags": ["API", "Getting Started"],
             "description": "Overview of Lekhak AI's public API."
           }
         },
         {
           "id": "auth_methods",
           "title": "Authentication Methods",
           "slug": "authentication",
           "markdownContent": "## Authentication\nLekhak AI API uses OAuth2 for authentication...",
           "lastModified": "2023-10-27T10:15:00Z",
           "status": "published",
           "metadata": {
             "author": "DocAI System",
             "tags": ["API", "Security"]
           }
         }
       ]
     }'
```

### POST /api/webhook

This endpoint is designed to receive external notifications or triggers. While its primary consumer might be `lekhak_ai` for event notifications (e.g., "documentation build complete, re-index now"), it can be configured to accept webhooks from other systems (e.g., GitHub, CI/CD pipelines) to trigger Pustak actions like rebuilding indexes, clearing caches, or initiating content refreshes.

*   **Purpose:** Process generic webhook events to trigger Pustak-specific actions.
*   **Method:** `POST`
*   **URL:** `https://pustak.example.com/api/webhook`

#### Request

**Headers:**
*   `Content-Type: application/json`
*   `X-API-Key: your_super_secret_pustak_api_key`
*   (Optional, but recommended for security) `X-Hub-Signature-256` or similar for payload verification if from a known service.

**Body (JSON):**

The structure of the webhook payload is flexible but typically includes an `eventType` and a `data` object relevant to the event.

```json
{
  "eventType": "string",           // REQUIRED. A string identifying the type of event (e.g., "DOC_UPDATED", "REPO_DELETED", "FULL_REINDEX", "CI_BUILD_SUCCESS").
  "timestamp": "ISO 8601 datetime",// REQUIRED. The time the event occurred (e.g., "2023-10-27T10:30:00Z").
  "origin": "string",              // OPTIONAL. The system that initiated the webhook (e.g., "lekhak_ai_core", "github_actions", "manual_trigger").
  "data": {                        // OPTIONAL. An object containing event-specific data.
    "repoName": "string",          // e.g., for "DOC_UPDATED" or "REPO_DELETED"
    "docType": "string",
    "version": "string",
    "documentIds": ["string"],     // List of specific document IDs affected, if applicable
    "triggerUser": "string",       // User who triggered the action, if known
    "commitHash": "string",        // For Git-related webhooks
    "url": "string",               // Link to the event source or affected resource
    "action": "string",            // Specific action performed, e.g., "published", "deleted"
    "message": "string"            // A descriptive message for the event
  },
  "signature": "string"            // OPTIONAL. A cryptographic signature to verify the sender's authenticity (e.g., HMAC-SHA256).
}
```

#### Response

**Success (HTTP 200 OK):**
```json
{
  "status": "received",
  "message": "Webhook event processed successfully.",
  "eventType": "DOC_UPDATED",
  "id": "webhook-event-uuid-12345" // A unique ID for this specific webhook event received by Pustak
}
```

**Error (HTTP 400 Bad Request or 500 Internal Server Error):**
```json
{
  "status": "error",
  "code": "UNKNOWN_EVENT_TYPE",
  "message": "The provided eventType 'UNSUPPORTED_EVENT' is not recognized.",
  "details": {
    "supportedEventTypes": ["DOC_UPDATED", "FULL_REINDEX"]
  }
}
```

#### Usage Example (cURL)

```bash
curl -X POST "https://pustak.example.com/api/webhook" \
     -H "Content-Type: application/json" \
     -H "X-API-Key: your_super_secret_pustak_api_key" \
     -d '{
       "eventType": "DOC_UPDATED",
       "timestamp": "2023-10-27T10:45:00Z",
       "origin": "lekhak_ai_core",
       "data": {
         "repoName": "lekhak-ai-core",
         "docType": "api-reference",
         "version": "v2.1",
         "documentIds": ["intro_to_api", "auth_methods"],
         "message": "API documentation for v2.1 updated and published."
       }
     }'
```

## 5. General Considerations

### Idempotency
The `/api/sync` endpoint is designed to be largely idempotent. Sending the same document `id` for a given `repoName`, `docType`, and `version` multiple times should result in the same state (the document being updated) without unintended side effects.

### Versioning
Pustak supports documentation versioning through the `version` field in the `/api/sync` endpoint and through its dynamic routing (`/repo/[repoName]/[docType]`). Future API versions will be indicated via path (`/v1/api/...`) or header (`Accept-Version: v1`).

### Rate Limiting
While not explicitly mentioned in the initial change, rate limiting will be implemented on these API endpoints in future iterations to prevent abuse and ensure stability. Consumers should be prepared to handle `429 Too Many Requests` responses.

### Data Validation
All incoming data is subject to strict validation. Requests with invalid or missing required fields will receive `400 Bad Request` responses.

### Auditing and Logging
All API requests are logged for auditing and debugging purposes, including the API key used (hashed), timestamps, and request payloads (redacted for sensitive information).
