## Current Architecture
The `docai_smart_wxyt73jp` (v10.4) project is a multi-language (Python, JavaScript, TypeScript) system built around a `FastAPI` powered `API` component, handling interactions from a `Frontend` and external systems. The core logic resides within a `Core` component, which is a collection of various `services` and `utilities` located under `src/core`, `src/services`, `src/references`, `src/integrations`, `src/processors`, and `src/utilities`.

The system leverages an event-driven paradigm, with `commit_bus` and `event_consumer` playing central roles in processing events. External integrations like `stripe_service`, `pustak_integration`, `lekhak_ai_integration`, `github_sync`, and `llm_provider_v2` (for AI models such as `google-generativeai`, `groq`, `openai`) are managed by specific utilities.

A dedicated set of `processors` (`doc_generation_endpoint`, `hierarchical_doc_generator`, `smart_processor`, `quality_integration`, `comprehensive_doc_generator`) handle complex tasks, particularly around documentation generation and quality assurance, likely utilizing AI/LLM capabilities and `universal_code_parser`. Data validation and schema definition are reinforced by `pydantic`, complementing the `canonical_model`.

Persistence is handled by a `Database` component, supporting a diverse range of technologies including `PostgreSQL`, `MySQL`, `SQLite`, `MongoDB`, `Redis`, and `Milvus`. Specifically, `asyncpg` suggests strong `PostgreSQL` usage for event-driven components like `commit_bus`, and `pymilvus` points to `Milvus` for RAG capabilities, likely used by the document generation processors. The system is designed for deployment across various cloud platforms and containerization technologies.

## Data Flow
1.  **Incoming Requests/Events**:
    *   The `Frontend` interacts with the `API` component through standard HTTP requests.
    *   `External Systems` (e.g., GitHub for code changes, Stripe for payments) send webhooks, which are received by `webhook_multi_org` and processed by `webhook_handler` within the `API`.
2.  **API Processing**:
    *   The `API` (built with `FastAPI`) routes requests to appropriate `services` (e.g., `auth_service`, `subscription_service`) or `utilities` (e.g., `main`, `github_sync`, `doc_generation_endpoint`).
3.  **Core Logic and Event Handling**:
    *   Business logic is executed by the various `services` and `utilities`.
    *   Events, such as new code commits, are likely published to the `commit_bus`.
    *   The `event_consumer` reads and processes events from the `commit_bus`, orchestrating actions like invoking `github_sync` to retrieve repository information, or interacting with `quality_checker`.
    *   Integration utilities (`stripe_service`, `pustak_integration`, `lekhak_ai_integration`, `llm_provider_v2`) communicate with respective external APIs.
4.  **Data Persistence**:
    *   Services and utilities interact with the `Database` component to store and retrieve application data. `canonical_model` provides the data schema.
    *   Specific database technologies like `PostgreSQL` (for `asyncpg`) are used for transactional data (e.g., event queues), and `Milvus` (for `pymilvus`) is utilized for vector embeddings, likely supporting AI-driven features like RAG.
5.  **Document Generation and AI Processing**:
    *   `universal_code_parser` extracts structured information from code.
    *   `doc_generation_endpoint` acts as an entry point for document generation requests.
    *   `hierarchical_doc_generator`, `smart_processor`, `quality_integration`, and `comprehensive_doc_generator` process data, potentially query `Milvus` for relevant information, and leverage `llm_provider_v2` to interact with large language models (`google-generativeai`, `groq`, `openai`) for generating comprehensive and high-quality documentation.
    *   `sentence-transformers` is used for creating embeddings, feeding into the RAG system.

## Recent Changes Impact
The v10.4 update, "Enhance Multi-Org Support and Event Processing Robustness", significantly strengthens the system's foundational capabilities for multi-tenancy and reliability.

1.  **Increased Event Processing Resilience in `src/core/commit_bus.py`**:
    *   The `get_unprocessed_commit_events` method now allows a higher `retry_count` (up to 5, from 3) for events. This change directly improves the fault tolerance of the event processing pipeline, enabling the system to recover more gracefully from transient failures without discarding important commit events.

2.  **Enhanced Multi-Organization GitHub Token Management in `src/core/event_consumer.py`**:
    *   The `get_github_token` method has been refactored to provide a more robust and flexible approach to retrieving GitHub tokens. It now prioritizes `github_access_token` from the `users` table and, if unavailable, intelligently falls back to an active `github_token` from the `user_github_tokens` table, using both `user_id` and `token_id`. This is crucial for securely and correctly managing GitHub access across different organizations and users.
    *   The `_process_event` method has been updated to pass the `github_token_id` extracted from the incoming event, enabling the new token retrieval logic. This ensures that the correct organization-specific or user-specific token is used for operations related to that event.

3.  **Multi-Organization Repository Synchronization State in `src/core/event_consumer.py` and Database**:
    *   The `mark_repo_processed` method now accepts and persists an `org_id` parameter when updating the `repo_sync_state` table. By using an `INSERT ... ON CONFLICT ... DO UPDATE` (upsert) statement, the system ensures that the `last_processed_sha` and crucially, the `org_id`, are correctly associated with each `repo_id`.
    *   This change is fundamental for supporting multiple organizations, as it allows the system to track the synchronization state of repositories distinctly for each organization, preventing data mix-ups or incorrect processing in a multi-tenant environment.
    *   **Database Impact**: This introduces a dependency on the `repo_sync_state` table having an `org_id` column, which may necessitate a database migration to add or modify this column.

Overall, these changes enhance the system's ability to operate reliably and securely in a multi-organizational context, particularly for event-driven GitHub repository synchronization.
