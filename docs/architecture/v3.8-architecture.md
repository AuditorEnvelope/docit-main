## Current Architecture
The system is built using a microservices architecture, with each service (e.g. stripe_service, auth_service) responsible for a specific functionality. The services interact with each other and with the database through APIs. The database is used to store and retrieve data, and is accessed through the services. The system also uses utilities (e.g. universal_code_parser, github_sync) to perform specific tasks.

## Data Flow
Data flows between the components as follows:
- The frontend sends requests to the api, which then calls the relevant service (e.g. stripe_service, auth_service).
- The service interacts with the database to retrieve or store data.
- The service then returns the data to the api, which sends it back to the frontend.
- The utilities (e.g. universal_code_parser, github_sync) are used by the services to perform specific tasks, and may interact with the database or other services.

## Recent Changes Impact
The recent changes introduce multi-organization support to the commit event processing system. This includes updates to the CommitEvent model, the CommitBusService, and the event consumer. The changes also add a new asynchronous get_github_token method to the EventConsumer, which is used to dynamically retrieve GitHub tokens based on the event context. The changes impact the data models, database schema, event processing logic, and security considerations around token management. A database migration is required for this feature to function.
