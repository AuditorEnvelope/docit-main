## Code Change Documentation: Critical Search Bug Fixes & Global Search Endpoint

### 1. Overview

This significant update addresses critical issues that rendered the application's search functionality unusable and introduces a powerful new global search capability. Previously, users encountered a non-functional frontend search bar and a missing backend API endpoint for global search queries.

This commit resolves these fundamental problems by:
*   Fixing frontend event handling to make the search bar interactive.
*   Introducing a new, robust backend API endpoint for global search.
*   Enhancing existing search endpoints with consistent validation.

The primary reason for the high significance of this change is its direct impact on core application utility. Search is a fundamental feature for any documentation platform, and its prior broken state severely limited user experience. The addition of global, repository-agnostic search significantly enhances the application's value.

### 2. Impact

This change has a substantial impact across key areas of the system:

*   **Search Functionality**: The core search mechanism is now fully operational and significantly enhanced.
*   **Frontend User Experience (UX)**: The search bar is now interactive, clickable, and visually responsive, improving overall navigation.
*   **Backend API**: A new public API endpoint has been added, and an existing one has been updated.
*   **Affected Components**:
    *   `pustak/src/app/page.tsx`: The main frontend page containing the search bar received critical event handling and styling fixes.
    *   `src/main.py`: The primary backend application file was updated to include the new global search endpoint and modifications to an existing one.
    *   `database_queries`: New SQL queries were introduced and existing ones refined for efficient and relevant search results against the `doc_nodes` table.

### 3. New Features

The following new functionalities have been introduced:

*   **Global Search Endpoint `/api/search`**: A new RESTful GET endpoint is now available to perform a comprehensive search across all documented content within the application.
*   **Repository-Agnostic Search**: The new global search allows users to find documentation regardless of the repository it belongs to, providing a unified search experience across the entire platform.
*   **Smart Ranking for Search Results**: Search results are intelligently ordered for relevance. Matches found in the `title` of a document are ranked highest, followed by matches in the `path`, and then matches within the `content`. This ensures users see the most pertinent results first.
*   **Minimum 3-Character Query Validation**: All search endpoints (`/api/search` and `/api/repos/{repo_name}/search`) now enforce a minimum query length of 3 characters. This prevents overly broad or inefficient searches and ensures more meaningful results.

### 4. Breaking Changes

**There are no breaking changes** introduced with this update. Existing `/api/repos/{repo_name}/search` users will observe a new validation rule for minimum query length, but this is a enhancement rather than a breaking change as it improves endpoint robustness.

### 5. Technical Details

**Frontend Fixes (`pustak/src/app/page.tsx`):**
The primary issue on the frontend was an unclickable search button and ineffective event handling. The following changes were implemented:
*   **`type='button'`**: Added to the search button element to prevent it from implicitly submitting a form, which was causing unexpected behavior.
*   **Robust Event Handling**: `e.preventDefault()` and `e.stopPropagation()` were strategically applied to ensure that click events are handled precisely by the intended elements, preventing event bubbling issues.
*   **`pointer-events-none`**: Critically, this CSS property was applied to child elements within the search button. This ensures that click events targeted at child elements (like icons or text spans) "fall through" to the parent button, guaranteeing the parent button's click handler receives the event.
*   **`cursor-pointer`**: Added for improved user experience, providing a visual cue that the search button is interactive.

**Backend Fixes & New Endpoint (`src/main.py`):**
A new global search endpoint was created, and existing validation was updated:
*   **New Endpoint `GET /api/search`**:
    *   This endpoint is responsible for performing a global, case-insensitive search across the `doc_nodes` database table.
    *   It searches across `title`, `content`, and `path` fields.
    *   **Minimum Query Validation**: It enforces a minimum query length of 3 characters. Queries shorter than this will result in a `400 Bad Request` error.
    *   **Smart Ranking**: Results are ordered by relevance:
        1.  Exact or partial matches in the `title` field are prioritized.
        2.  Matches in the `path` field are next.
        3.  Matches in the `content` field follow.
    *   **Result Limit**: The endpoint limits the number of returned search results to 50 to ensure performance and manage response size.
    *   **Error Handling**: Robust error handling is implemented for database operations, returning appropriate HTTP status codes and messages in case of failures.
*   **Update to `/api/repos/{repo_name}/search`**:
    *   The existing repository-specific search endpoint was updated to include the same minimum 3-character query validation for consistency across all search functionalities.

### 6. Usage Examples

#### **Frontend Interaction:**

Users can now simply click the search bar, type their query (minimum 3 characters), and press Enter or click the search icon. The frontend will handle the query and display results based on the new global search API.

#### **Backend API (Global Search):**

To perform a global search, send a `GET` request to the `/api/search` endpoint with a `q` query parameter.

**Request:**
```http
GET /api/search?q=installing+pustak HTTP/1.1
Host: your-application-url.com
```

**Example Response (Status: 200 OK):**
```json
[
  {
    "repo_name": "pustak-core",
    "doc_id": "getting-started",
    "title": "Installing Pustak",
    "path": "/getting-started/installation.md",
    "excerpt": "To begin installing pustak, first ensure you have Python 3.8+...",
    "url": "/docs/pustak-core/getting-started/installation"
  },
  {
    "repo_name": "pustak-cli",
    "doc_id": "setup",
    "title": "CLI Setup Guide",
    "path": "/cli/setup.md",
    "excerpt": "This guide covers installing the pustak CLI tool and configuring your environment...",
    "url": "/docs/pustak-cli/cli/setup"
  }
]
```

**Error Response (Status: 400 Bad Request - Query too short):**
```http
GET /api/search?q=in HTTP/1.1
Host: your-application-url.com
```

**Example Error Response:**
```json
{
  "detail": "Search query must be at least 3 characters long."
}
```

### 7. Testing

To ensure the stability and correct functionality of these changes, the following test cases should be performed:

#### **Frontend Tests:**

1.  **Search Bar Clickability**: Verify that the search bar and its associated icon/button are now clickable and visually respond to user interaction (e.g., cursor changes to pointer).
2.  **Basic Search**: Enter a valid query (e.g., "installation", "API reference") into the search bar and press Enter. Verify that search results are displayed.
3.  **Short Query Handling**: Enter a query with fewer than 3 characters (e.g., "ab", "a") and attempt to search. Verify that an appropriate client-side or server-side error message is displayed, indicating the minimum query length requirement.
4.  **No Results**: Search for a string that is unlikely to exist in any documentation. Verify that a "No results found" message or similar is displayed gracefully.
5.  **Focus and Keyboard Navigation**: Ensure that the search bar can be focused using keyboard (e.g., Tab key) and that pressing Enter triggers a search.

#### **Backend API Tests:**

1.  **Global Search (`GET /api/search`) - Valid Query**:
    *   Test with a query of 3+ characters (e.g., `?q=pustak`).
    *   Test with a multi-word query (e.g., `?q=api+endpoint`).
    *   Verify that results are returned with `repo_name`, `doc_id`, `title`, `path`, `excerpt`, and `url` fields.
    *   Check for case-insensitivity (e.g., `?q=PYTHON` should match "python").
2.  **Global Search (`GET /api/search`) - Short Query**:
    *   Test with queries shorter than 3 characters (e.g., `?q=a`, `?q=ab`).
    *   Verify that the API returns a `400 Bad Request` status code with the expected error message: `"Search query must be at least 3 characters long."`.
3.  **Global Search (`GET /api/search`) - Relevance Ranking**:
    *   Formulate queries where the search term appears in the title of one document, the path of another, and the content of a third.
    *   Verify that results are ordered correctly: title matches first, then path, then content.
    *   Example: Search for a term that is the exact title of one document and appears only in the content of another. The title-matching document should be higher ranked.
4.  **Global Search (`GET /api/search`) - Result Limit**:
    *   If possible, populate the database with enough documents to exceed 50 results for a common query.
    *   Verify that the endpoint returns a maximum of 50 results.
5.  **Repository-Specific Search (`GET /api/repos/{repo_name}/search`) - Short Query**:
    *   Test `GET /api/repos/my-repo/search?q=ab`.
    *   Verify that it returns a `400 Bad Request` with the same "Search query must be at least 3 characters long." message.
6.  **Database Connection Errors**: Simulate a database connection issue or an invalid query execution within the backend search logic (e.g., by temporarily disabling the database or introducing a syntax error in the SQL). Verify that the API returns a `500 Internal Server Error` and handles the exception gracefully without exposing sensitive information.
7.  **Empty Database**: Test search queries against an empty `doc_nodes` table. Verify that an empty list of results `[]` is returned (200 OK) rather than an error.
