## Webhook Processing & CORS Security Enhancement

### 1. Overview

This update addresses critical issues related to API security (CORS) and the core functionality of the multi-organization webhook system. The primary goal is to tighten security by restricting Cross-Origin Resource Sharing (CORS) to known trusted sources, and to significantly improve the robustness and reliability of webhook event processing. These changes ensure that webhook events are correctly processed, accurately attributed to the respective users and organizations, and have access to necessary GitHub tokens, which is fundamental for the application's operation, especially in multi-organization environments.

The commit specifically resolves reported "CORS and webhook issues" by:
*   Strengthening CORS security to prevent unauthorized access.
*   Making webhook event processing more robust for multi-organization scenarios, including improved fallback mechanisms for user attribution.
*   Enhancing webhook registration to ensure proper attribution of events to users and their GitHub tokens, by explicitly linking registered organizations to their webhooks and associated tokens.

### 2. Impact

This change has a broad impact across several core functionalities of the system:

*   **Security:** Significantly improved by restricting allowed CORS origins.
*   **Webhooks:** Core webhook event processing and registration logic are updated for robustness and correct attribution.
*   **Authentication:** The authentication response now includes the GitHub token, affecting client-side handling of user data.
*   **Data Consistency:** Improved consistency in `org_webhooks` and `org_registrations` tables.
*   **Multi-Org Support:** Enhanced reliability for attributing webhook events to correct users and organizations.

**Affected Components:**

*   `src/core/auth_service.py`: Authentication response structure.
*   `src/main.py`: FastAPI application configuration (CORS), webhook event processing, and webhook registration endpoint logic.
*   `src/webhooks/webhook_multi_org.py`: Utility functions for retrieving webhook context.

### 3. New Features

The following new functionalities and improvements have been introduced:

*   **GitHub Token in Auth Service Response:** The `login_and_create_jwt` method in the authentication service now includes the user's `github_token` in the successful login response payload. This provides immediate access to the GitHub token for client-side operations post-authentication.
*   **Robust Multi-Org Webhook Event Attribution:** Enhanced logic in `process_commit_event` to derive the `user_id` for an event even when the `webhook_context` is initially incomplete. It now includes a fallback mechanism to query the `org_registrations` table based on the `repo_org` to ensure proper event attribution.
*   **Explicit Webhook Registration into `org_webhooks` Table:** During the initial setup via the `register_webhook` endpoint, the system now explicitly inserts or updates a record in the `org_webhooks` table. This ensures comprehensive registration, including fetching the `token_id` from `user_github_tokens` and linking it to the organization's webhook for robust event processing.

### 4. Breaking Changes

**None.**

This change introduces no breaking changes to existing APIs or database schemas. All changes are backward-compatible. Existing clients will continue to function, though they can now leverage the new `github_token` in the auth response.

### 5. Technical Details

1.  **CORS Configuration (`src/main.py`):**
    *   The `CORSMiddleware` `allow_origins` setting has been restricted from `["*"]` (allowing all origins) to a specific, predefined list of local development/testing URLs.
    *   **New `allow_origins` list:** `["http://localhost:3000", "http://localhost:8000", "http://127.0.0.1:3000", "http://127.0.0.1:8000", "http://192.168.1.2:3000", "http://192.168.1.2:8000"]`.
    *   This significantly enhances security by preventing arbitrary cross-origin requests and restricting access to known, trusted development/testing environments. For production, this list should be updated to include the actual deployed frontend URLs.

2.  **Auth Service Response (`src/core/auth_service.py`):**
    *   The `login_and_create_jwt` method now includes `github_token` in the dictionary returned upon successful authentication.
    *   The response payload now looks like: `{"access_token": "...", "refresh_token": "...", "expires_in": ..., "github_token": "..."}`.

3.  **Robust Webhook Event Processing (`src/main.py` - `process_commit_event`):**
    *   Within the `process_commit_event` function, new logic has been implemented to derive the `user_id`.
    *   If `webhook_context.user_id` is not available, the system now queries the `org_registrations` table using `repo_org` (organization name derived from the webhook payload) to find an associated `user_id`.
    *   This ensures that commit events are properly attributed to a `user_id` even if the initial webhook context is incomplete or lacks direct `user_id` information.

4.  **Comprehensive Webhook Registration (`src/main.py` - `register_webhook`):**
    *   The `register_webhook` endpoint has been enhanced to perform two key actions:
        1.  Register/update the organization in the `org_registrations` table.
        2.  **Explicitly insert or update a record in the `org_webhooks` table.**
    *   During the `org_webhooks` registration, the `token_id` associated with the registering `user_id` is fetched from `user_github_tokens` and included.
    *   This ensures the `org_webhooks` table contains comprehensive information: `user_id`, `org_id`, `webhook_secret`, and `github_token_id`, which is vital for subsequent webhook event processing and correct token retrieval.

5.  **Enhanced Webhook Context Retrieval (`src/webhooks/webhook_multi_org.py`):**
    *   The `get_org_context_from_repo` utility function has been improved for resilience.
    *   If the organization's context (e.g., associated user and token) is not found directly in `org_webhooks` using the repository's organization name, it now attempts a fallback:
        1.  Finds the `user_id` and `org_id` in `org_registrations`.
        2.  Uses the found `user_id` to retrieve the `token_id` from `user_github_tokens`.
    *   This provides a more robust lookup mechanism, ensuring that incoming webhook events can retrieve necessary contextual information even with varied registration states.

### 6. Usage Examples

#### 6.1. Client-Side Authentication Response

When a client successfully authenticates, the response payload will now include the `github_token`:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 3600,
  "github_token": "ghs_YOUR_GITHUB_PERSONAL_ACCESS_TOKEN"
}
```

Clients can now directly access `response.github_token` for GitHub API calls, simplifying workflows that require immediate access to the user's GitHub token post-login.

#### 6.2. Webhook Registration Endpoint

When registering a webhook (e.g., via the `/register_webhook` endpoint), the internal process now automatically handles the comprehensive registration into the `org_webhooks` table. No changes are required for the client-side request to `/register_webhook`.

The system will internally:
1.  Verify the user's `github_token`.
2.  Create/update an entry in `org_registrations`.
3.  Create/update an entry in `org_webhooks` linking `user_id`, `org_id`, generated `webhook_secret`, and the `token_id` of the GitHub token used for registration.

This ensures that any subsequent GitHub webhook events from that organization will have the necessary context (user, org, and associated GitHub token) for processing.

#### 6.3. CORS Configuration (Developer Information)

When developing frontend applications that interact with this backend, ensure your development server's origin (e.g., `http://localhost:3000`) is included in the `allow_origins` list in `src/main.py`.

If your frontend is hosted on an origin *not* in this list, you will encounter CORS errors in your browser console, preventing requests to the backend. For example, if your frontend is at `http://my-dev-app.com:4000`, you would need to add `"http://my-dev-app.com:4000"` to the `allow_origins` list in `src/main.py`.

### 7. Testing

To ensure the stability and correctness of these changes, the following testing scenarios are recommended:

1.  **CORS Configuration:**
    *   **Success:** Access the API from a frontend application running on `http://localhost:3000` or `http://127.0.0.1:8000`. Verify that API requests (e.g., login, registering webhook) complete successfully without CORS errors.
    *   **Failure:** Attempt to access the API from an origin *not* in the `allow_origins` list (e.g., a simple HTML page opened directly from the file system, or a different local port like `http://localhost:4000`). Verify that requests are blocked by CORS policies and corresponding errors appear in the browser console.

2.  **Authentication Service Response:**
    *   Perform a successful user login.
    *   Inspect the JSON response payload to confirm the presence and correctness of the `github_token` alongside `access_token`, `refresh_token`, and `expires_in`.

3.  **Webhook Registration and Event Processing (Multi-Org Scenarios):**
    *   **Scenario A (Clean Registration):**
        *   Register a new GitHub organization webhook via the `/register_webhook` endpoint.
        *   Verify that entries are created/updated in both `org_registrations` and `org_webhooks` tables, with correct `user_id`, `org_id`, `webhook_secret`, and crucially, a valid `github_token_id` in `org_webhooks`.
        *   Manually trigger a `push` event (or other relevant event) from the registered GitHub repository.
        *   Monitor the backend logs to confirm `process_commit_event` correctly attributes the event to the `user_id` and `org_id`.
    *   **Scenario B (Resilience Testing - Incomplete Context):**
        *   (Simulate) a webhook event where the initial `webhook_context` might be missing `user_id` but contains `repo_org`.
        *   Verify that the system can still look up the `user_id` via `org_registrations` and process the event correctly. This might require mocking `get_org_context_from_repo` or directly calling `process_commit_event` with a manipulated context in a test environment.
    *   **Scenario C (Multiple Organizations):**
        *   Register webhooks for two distinct GitHub organizations (Org A and Org B) using different or the same user accounts.
        *   Trigger events from repositories in both Org A and Org B.
        *   Verify that events from Org A are correctly attributed to its `user_id` and `github_token`, and similarly for Org B, ensuring no cross-organization data leakage or incorrect attribution.

### 8. Migration Guide

**No specific migration steps are required.**

This update does not introduce any breaking changes to the database schema or API contracts that would necessitate a migration guide for existing deployments. The changes are internal enhancements and security improvements.

*   Existing frontend applications will continue to function. They can optionally be updated to consume the `github_token` from the login response if needed.
*   Existing webhook registrations and event processing will benefit from the enhanced robustness automatically.
*   For new deployments or updating existing `src/main.py` files, ensure the `allow_origins` list for `CORSMiddleware` is correctly configured for your environment (development, testing, production).
