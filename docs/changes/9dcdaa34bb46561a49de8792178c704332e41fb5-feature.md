# Multi-Organization Commit Bus Integration and Dynamic Token Retrieval
## Overview
This commit introduces a significant architectural feature to the commit event processing system, enabling support for multiple organizations. Each organization can now have its own repository configurations and authentication tokens. This change extends the `CommitEvent` model, updates database operations, and modifies the event consumer to dynamically fetch the appropriate GitHub token for event processing.

The primary motivation behind this feature is to enhance the system's scalability and security by allowing it to handle multiple organizations with distinct authentication tokens. This change impacts various components of the system, including data models, database schema, event processing logic, and security considerations around token management.

## Impact
The following components of the system are affected by this change:
* **Data Models**: The `CommitEvent` model has been extended with new fields.
* **Database Schema**: The `commit_events` table has been updated to store the new context fields, and a `user_github_tokens` table is implied for token storage.
* **Event Processing**: The event consumer logic has been modified to dynamically retrieve GitHub tokens based on event context.
* **Security**: Token management has been enhanced with a fallback mechanism for GitHub token retrieval.
* **Scalability**: The system can now support multiple organizations, improving its overall scalability.

## New Features
The following new features have been added:
* **Multi-organization context for commit events**: The `CommitEvent` model now includes fields for `user_id`, `org_id`, `github_token_id`, and `webhook_secret`.
* **Persistence of multi-org context in commit_events database table**: The `commit_events` table has been updated to store the new context fields.
* **Dynamic retrieval of GitHub tokens based on event context**: The `EventConsumer` can now query a `user_github_tokens` table for a specific GitHub token using `user_id` and `token_id`.
* **Fallback mechanism for GitHub token retrieval**: If no specific token is found or provided, the system falls back to using the `GITHUB_TOKEN` environment variable.

## Breaking Changes
There are no breaking changes introduced by this commit. The new fields added to the `CommitEvent` model are marked as `Optional` to ensure backward compatibility.

## Technical Details
The implementation specifics are as follows:
* The `CommitEvent` Pydantic model has been expanded with `user_id`, `org_id`, `github_token_id`, and `webhook_secret` fields, all marked as `Optional`.
* The `CommitBusService`'s `insert_event` and `get_pending_events` methods have been updated to handle the new fields, requiring corresponding column additions to the `commit_events` database table.
* A new asynchronous `get_github_token` method has been added to `EventConsumer` to query a `user_github_tokens` table for a specific GitHub token using `user_id` and `token_id`.
* The `process_event` method in `EventConsumer` now extracts the context fields from incoming events and attempts to retrieve a specific GitHub token using `get_github_token`. If no specific token is found or provided, it falls back to using the `GITHUB_TOKEN` environment variable.

## Usage Examples
To use the new features, follow these steps:
1. Create a new `CommitEvent` instance with the required context fields (e.g., `user_id`, `org_id`, `github_token_id`, and `webhook_secret`).
2. Insert the event into the `commit_events` table using the updated `CommitBusService` methods.
3. Configure the `EventConsumer` to use the new `get_github_token` method to retrieve the appropriate GitHub token for event processing.
