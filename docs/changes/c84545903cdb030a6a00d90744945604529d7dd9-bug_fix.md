# Documentation: Event Processing Resilience & Multi-Org GitHub Token Handling Enhancements

## 1. Overview

This change significantly enhances the robustness and correctness of the commit event processing pipeline. It addresses critical aspects of system reliability and correctness by increasing retry attempts for failed events, implementing a more resilient GitHub token retrieval mechanism with a fallback for multi-organization contexts, and improving repository synchronization state management.

The primary goals of this update are:
*   **Mitigate Transient Errors**: By allowing more retries for event processing failures.
*   **Improve Multi-Organization Support**: Ensuring the system can reliably acquire valid GitHub tokens for API interactions across various organizations.
*   **Ensure Data Integrity**: Through more robust tracking of repository synchronization states.

## 2. Impact

This change primarily impacts the core event processing logic, GitHub integration, and underlying database interactions related to synchronization states.

**Impact Scope:**
*   **Event Processing**: Increased resilience and retry mechanisms.
*   **GitHub Integration**: More robust and context-aware token retrieval.
*   **Data Integrity**: Enhanced consistency for repository synchronization states.
*   **Resilience**: Overall system's ability to recover from transient failures.
*   **Multi-Organization Support**: Improved handling of GitHub API authentication in diverse organizational setups.

**Affected Components:**
*   `src/core/commit_bus.py`: Logic for fetching and managing commit events.
*   `src/core/event_consumer.py`: Core event processing, GitHub token retrieval, and repository state management.
*   `database_interactions`: Specifically affecting `users`, `user_github_tokens`, and `repo_sync_state` tables.

## 3. New Features

### Improved Multi-Organization GitHub Token Fallback Mechanism

A key new feature is the enhanced `get_github_token` logic within `event_consumer.py`. This mechanism now provides a more robust and flexible way to acquire GitHub tokens, especially critical for environments supporting multiple organizations or where users might have different token configurations.

The system will now attempt to retrieve a GitHub token using a two-tiered approach:
1.  **Primary Attempt**: Fetch the `github_access_token` directly from the `users` table, associated with the `user_id` of the event.
2.  **Fallback Attempt**: If the primary token is not found, the system will attempt to retrieve an organization-specific token from the `user_github_tokens` table, using both the `user_id` and a provided `token_id` (extracted from the event payload). This ensures that even if a user doesn't have a global `github_access_token`, an organization-specific token can still be used for GitHub API interactions.

This provides greater resilience and flexibility, crucial for seamless operation in multi-organizational setups.

## 4. Breaking Changes

**No breaking changes** are introduced with this update.
Existing functionality, data structures, and APIs will continue to operate as before. The changes are entirely additive and enhance internal system robustness without requiring any modifications to existing integrations or configurations.

## 5. Technical Details

### 5.1. Increased Event Processing Retries (`src/core/commit_bus.py`)

The SQL query responsible for fetching unprocessed commit events has been modified to allow for more retry attempts.
*   **Previous Logic**: Events with `retry_count < 3` were eligible for reprocessing.
*   **New Logic**: Events with `retry_count < 5` are now eligible.

This change significantly improves the system's resilience to transient processing failures, such as temporary network issues, GitHub API rate limits, or momentary database unavailability, by providing more opportunities for successful processing.

### 5.2. Enhanced GitHub Token Retrieval (`src/core/event_consumer.py`)

The `get_github_token` function now incorporates the new fallback mechanism:
1.  It first queries the `users` table for `github_access_token` based on `user_id`.
2.  If the primary token is `NULL` or not found, it then queries the `user_github_tokens` table, using both `user_id` and the `github_token_id` passed from the event. This allows for specific tokens linked to organizations or contexts to be retrieved.

### 5.3. Refined Event Processing (`src/core/event_consumer.py`)

The `process_event` method has been updated to extract the `github_token_id` from the incoming event payload. This `github_token_id` is then passed to the `get_github_token` function, enabling the newly implemented fallback logic to correctly identify and retrieve the appropriate GitHub token for API interactions.

### 5.4. Robust Repository Sync State Management (`src/core/event_consumer.py`)

The method `mark_repo_processed` has been significantly enhanced to ensure data integrity and better multi-organization context for repository synchronization states.
*   **Previous Logic**: A simple `UPDATE` statement was used, which could fail if a `repo_sync_state` record didn't exist for a given `repo_id` and `org_id`.
*   **New Logic**: An `INSERT ... ON CONFLICT (repo_id) DO UPDATE ...` (upsert) statement is now used. This ensures:
    *   If a `repo_sync_state` record for the `repo_id` and `org_id` combination does not exist, a new one is created.
    *   If it does exist, the existing record is updated with the new `last_processed_commit_sha`.
*   Crucially, `org_id` is now explicitly included in this operation, providing accurate tracking of processing progress for repositories across different organizations.

## 6. Usage Examples

The changes primarily affect the internal workings of the event processing system, so direct "usage" by end-users or external developers is minimal. However, understanding the new behavior is important.

### 6.1. Event Processing Retries

When an event fails to process due to a transient error, the system will now automatically attempt to reprocess it up to 4 more times (for a total of 5 attempts) before marking it as permanently failed. This means fewer events will require manual intervention after temporary outages.

**Example (Internal System Flow):**
1.  An event is fetched by `commit_bus.py` with `retry_count = 0`.
2.  `event_consumer.py` attempts to process it, but a GitHub API rate limit is hit. The processing fails.
3.  The `retry_count` for this event is incremented to 1.
4.  Later, `commit_bus.py` fetches the event again (since `retry_count < 5`).
5.  This process repeats. If the event fails 5 times, it will no longer be eligible for automatic retries.

### 6.2. GitHub Token Retrieval

The `process_event` method now intelligently requests a GitHub token.

**Conceptual Code Snippet (from `event_consumer.py`):**

```python
# Assuming 'event_data' is the parsed incoming event payload
user_id = event_data.get('user_id')
github_token_id = event_data.get('github_token_id') # New: Extracted from event

# Call the enhanced token retrieval function
github_token = self.get_github_token(user_id=user_id, github_token_id=github_token_id)

if not github_token:
    # Handle error: no valid token found
    logger.error(f"No GitHub token found for user_id: {user_id}, token_id: {github_token_id}")
    return # Event processing fails

# Use the retrieved token for GitHub API interactions
github_client = GitHubClient(token=github_token)
```

This means that if an event originates from an organization that has a specific `github_token_id` configured, that ID will be passed, ensuring the correct token is retrieved even if the user doesn't have a default personal access token.

### 6.3. Repository Sync State Management

The `mark_repo_processed` method now ensures that the `repo_sync_state` is always correctly managed, whether it's a new repository or an existing one, and correctly associates it with the organization.

**Conceptual Code Snippet (from `event_consumer.py`):**

```python
repo_id = event_data.get('repo_id')
org_id = event_data.get('org_id')
last_processed_commit_sha = event_data.get('commit_sha')

# This method internally uses the upsert logic
self.mark_repo_processed(
    repo_id=repo_id,
    org_id=org_id,
    last_processed_commit_sha=last_processed_commit_sha
)

# Database interaction (internal to mark_repo_processed) would look like:
# INSERT INTO repo_sync_state (repo_id, org_id, last_processed_commit_sha, updated_at)
# VALUES (:repo_id, :org_id, :last_processed_commit_sha, NOW())
# ON CONFLICT (repo_id) DO UPDATE SET
#   org_id = EXCLUDED.org_id, # org_id can be updated if the repo moves orgs or if it's implicitly part of a single user org
#   last_processed_commit_sha = EXCLUDED.last_processed_commit_sha,
#   updated_at = EXCLUDED.updated_at
# WHERE repo_sync_state.org_id = EXCLUDED.org_id; # Ensure we update the correct org's state if a repo can be associated with multiple orgs
```
**Note:** The `ON CONFLICT (repo_id)` means the `repo_id` is the unique key for conflict resolution. The `org_id` is part of the `UPDATE SET` clause, ensuring that if a record exists for a `repo_id`, its associated `org_id` and `last_processed_commit_sha` are correctly updated within that unique record. This maintains a single sync state per repository, correctly attributed to its `org_id`.

## 7. Testing

To ensure the new functionality and enhancements are working as expected, the following testing scenarios are recommended:

### 7.1. Event Processing Retries

*   **Test Case 1: Transient Failure & Recovery**
    *   **Setup**: Artificially introduce a transient error (e.g., temporary database connection issue, mock GitHub API failure) for an event processing attempt.
    *   **Expected Behavior**: The event should be retried up to 5 times. If the transient issue resolves within these retries, the event should eventually process successfully.
*   **Test Case 2: Persistent Failure**
    *   **Setup**: Introduce a persistent error (e.g., invalid event data that always causes an error) for an event.
    *   **Expected Behavior**: The event should be retried 5 times, failing each time. After the 5th failure, it should no longer be eligible for automatic reprocessing by `commit_bus.py`.
*   **Monitoring**: Verify the `retry_count` column in the database is correctly incremented.

### 7.2. GitHub Token Retrieval

*   **Test Case 1: Primary Token Exists**
    *   **Setup**: A user has a valid `github_access_token` in the `users` table. The event may or may not include a `github_token_id`.
    *   **Expected Behavior**: `get_github_token` should successfully retrieve the token from the `users` table.
*   **Test Case 2: Fallback Token Used (Multi-Org Context)**
    *   **Setup**: A user does *not* have a `github_access_token` in the `users` table, but has a valid token in the `user_github_tokens` table for a specific `github_token_id`. The event payload includes this `github_token_id`.
    *   **Expected Behavior**: `get_github_token` should successfully retrieve the token from `user_github_tokens`.
*   **Test Case 3: `github_token_id` is `NULL` or missing from event**
    *   **Setup**: A user does *not* have a `github_access_token` in the `users` table, and the event does not provide a `github_token_id`.
    *   **Expected Behavior**: `get_github_token` should return `None` or raise an appropriate error, indicating no token could be found.
*   **Test Case 4: Invalid `github_token_id`**
    *   **Setup**: The event includes a `github_token_id` that does not exist in `user_github_tokens` for the given `user_id`.
    *   **Expected Behavior**: `get_github_token` should fail to find a token and return `None` or raise an error.
*   **Integration**: Verify that `process_event` correctly passes `github_token_id` to `get_github_token`.

### 7.3. Repository Sync State Management

*   **Test Case 1: Initial Repository Processing (New `repo_sync_state` entry)**
    *   **Setup**: Process an event for a `repo_id` and `org_id` combination that does not yet exist in the `repo_sync_state` table.
    *   **Expected Behavior**: A new record should be created in `repo_sync_state` with the correct `repo_id`, `org_id`, and `last_processed_commit_sha`.
*   **Test Case 2: Subsequent Repository Processing (Update existing entry)**
    *   **Setup**: Process an event for a `repo_id` and `org_id` combination that already exists in `repo_sync_state`, with a new `last_processed_commit_sha`.
    *   **Expected Behavior**: The existing `repo_sync_state` record should be updated with the new `last_processed_commit_sha` and `updated_at` timestamp. The `org_id` should remain consistent.
*   **Test Case 3: Multi-Organization Context**
    *   **Setup**: Process events for the same `repo_id` but associated with different `org_id` values (if applicable for your data model, though `repo_id` as primary key implies one org per repo for `repo_sync_state`). Or, more commonly, process events for distinct `repo_id`/`org_id` pairs.
    *   **Expected Behavior**: Each unique `repo_id`/`org_id` pair should maintain its independent and correct `repo_sync_state`.
