# Documentation: Enhanced GitHub Token Retrieval and Repository Synchronization State Management

## 1. Overview

This update introduces significant enhancements to the way the system handles GitHub token retrieval and manages the synchronization state of repositories. The changes primarily focus on increasing flexibility, robustness, and scalability, especially in environments with multiple organizations or specialized token requirements.

Specifically, this enhancement:

*   Improves fault tolerance in commit event processing by increasing retry attempts.
*   Enhances GitHub token retrieval by allowing the system to fallback to organization-specific tokens if the user's main token is not available.
*   Improves the reliability of repository synchronization tracking by using an "upsert" approach and including the organization ID in the state management.

These changes are crucial for ensuring the reliable and efficient processing of GitHub events and maintaining accurate synchronization status across various projects.

## 2. Impact

This change impacts the following areas of the system:

*   **GitHub Integration:**  The way we authenticate with GitHub and retrieve data from repositories.
*   **Event Processing:** The handling of commit events and their associated data.
*   **Data Persistence:**  The storage and retrieval of user tokens and repository synchronization states.
*   **Multi-Organization Support:** The ability to manage repositories and events from multiple GitHub organizations independently.

The following components were directly modified:

*   `src/core/commit_bus.py`:  Increased event retry attempts.
*   `src/core/event_consumer.py`: Refactored GitHub token retrieval and repository synchronization state management.
*   **Database:** Modifications to the `users`, `user_github_tokens`, and `repo_sync_state` tables.

## 3. New Features

This update introduces the following new features:

*   **Flexible GitHub Token Retrieval:** The system can now retrieve a user's primary GitHub token (`github_access_token` from the `users` table). If this token is not available, it can fall back to retrieving a specific token from the `user_github_tokens` table using the `user_id` and `token_id`.  This enables scenarios where different tokens are required for different organizations or installations.
*   **Robust Repository Sync State Management (Upsert):**  The system now uses an `INSERT ... ON CONFLICT ... DO UPDATE` (upsert) statement to manage the `repo_sync_state` records. This ensures that a record is always created or updated, preventing potential data inconsistencies.
*   **Organization ID in Repository Sync State:** The `repo_sync_state` table now includes the `org_id` column, providing context for repositories in multi-organization environments.  This allows the system to correctly track synchronization status for the same repository across different organizations.
*   **Increased Event Retry Count**: The `CommitBusService` now retries processing commit events 5 times instead of 3, providing greater resilience to temporary failures.

## 4. Breaking Changes

This update **does not introduce any breaking changes**. Existing functionality remains compatible with the new features. However, database schema modifications are present, which need to be handled during deployment.

## 5. Technical Details

### 5.1 CommitBusService - Increased Retry Attempts

The `CommitBusService` in `src/core/commit_bus.py` was updated to increase the maximum number of retry attempts for processing failed commit events.

```python
# Previous code (example)
max_retries = 3

# New code
max_retries = 5
```

This change increases the likelihood of successfully processing events that initially fail due to transient issues, such as temporary network connectivity problems.

### 5.2 EventConsumer - Enhanced GitHub Token Retrieval

The `EventConsumer.get_github_token` method in `src/core/event_consumer.py` was refactored to prioritize the user's main token and then fallback to organization-specific tokens.

```python
async def get_github_token(self, user_id: int, github_token_id: Optional[int] = None) -> Optional[str]:
    """
    Retrieves the GitHub token for a user.  Prioritizes the main token,
    then falls back to a specific token if provided.
    """
    async with self.db_session() as session:
        # First, try to get the user's main token
        user = await session.get(User, user_id)
        if user and user.github_access_token:
            return user.github_access_token

        # If the main token is not available, try to get the specific token
        if github_token_id:
            token_entry = await session.get(UserGithubToken, github_token_id)
            if token_entry:
                return token_entry.github_token

        return None
```

This change allows for more flexible token management and enables the use of specific tokens for different organizations or installations. The `process_event` function was adjusted to pass the `github_token_id` to this function if available.

### 5.3 EventConsumer - Robust Repository Sync State Management

The `EventConsumer.mark_repo_processed` method in `src/core/event_consumer.py` was updated to use an "upsert" statement and to include the organization ID.

```python
async def mark_repo_processed(self, repo_id: int, org_id: int):
    """
    Marks a repository as processed in the repo_sync_state table,
    either by inserting a new record or updating an existing one.
    Includes the organization ID for context.
    """
    async with self.db_session() as session:
        stmt = insert(RepoSyncState).values(
            repo_id=repo_id, org_id=org_id, last_synced=datetime.utcnow()
        ).on_conflict_do_update(
            index_elements=[RepoSyncState.repo_id],
            set_=dict(last_synced=datetime.utcnow())
        )
        await session.execute(stmt)
        await session.commit()
```

This change ensures that the `repo_sync_state` table always contains a record for each repository being tracked and includes the relevant organization ID.  This significantly improves data consistency and enables better tracking of repository synchronization status in multi-organization environments.  Calls to this method in the `process_repo_update` function were modified to pass the `org_id`.

### 5.4 Database Schema Changes

The `repo_sync_state` table has been modified to include the `org_id` column:

```sql
-- Example SQL migration
ALTER TABLE repo_sync_state ADD COLUMN org_id INTEGER;
```

This new column is essential for correctly tracking repository synchronization status in multi-organization environments. The primary key may also need to be updated to include the `org_id`, depending on existing data structures. Consider adding a composite key of `repo_id` and `org_id` for uniqueness.

## 6. Usage Examples

### 6.1 Using Organization-Specific Tokens

1.  Store organization-specific GitHub tokens in the `user_github_tokens` table, associating them with the appropriate `user_id` and assigning a unique `id` to each token (which will be the `github_token_id`).
2.  When creating or processing GitHub events related to that organization, ensure the event payload includes the `github_token_id` associated with that token.
3. The `EventConsumer.process_event` function will now automatically fetch the correct token from the `user_github_tokens` table based on the provided `github_token_id` when calling `get_github_token`.

### 6.2 Tracking Repository Synchronization in Multi-Organization Environments

The `EventConsumer.mark_repo_processed` method now requires the `org_id` parameter.  Ensure that the correct `org_id` is passed when calling this method to accurately track synchronization status for each repository in its respective organization. This will automatically create/update the `repo_sync_state` record with the appropriate `org_id`, allowing for proper synchronization tracking.
