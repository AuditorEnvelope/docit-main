# Event Processing Reliability and Multi-Organization Support Enhancements

## 1. Overview

This release significantly upgrades the robustness and reliability of our event processing infrastructure, particularly focusing on how events are handled and how GitHub tokens are managed in multi-organization environments. The core motivation behind these changes is to address critical aspects of system stability and correctness, ensuring more reliable event processing and accurate data management within a multi-tenant/multi-organization architecture. The enhanced token retrieval and robust sync state updates directly contribute to the system's operational integrity.

## 2. Impact

These changes have a broad impact across critical system components:

*   **Event Processing**: The core mechanism for handling incoming events has been made more resilient to transient failures.
*   **GitHub API Integration**: The system's ability to interact with the GitHub API, especially in contexts involving multiple organizations or user tokens, has been improved.
*   **Database Persistence**: How repository synchronization state is stored and managed in the database is now more robust and idempotent.
*   **Multi-Organization Support**: Specific improvements directly enhance the system's performance and accuracy when dealing with data across multiple organizational contexts.

**Affected Components:**

*   `src/core/commit_bus.py`
*   `src/core/event_consumer.py`

## 3. New Features

This update introduces several key enhancements:

*   **Increased Event Retry Attempts**: The system will now retry event processing more times before marking an event as permanently failed, reducing data loss due to transient issues.
*   **More Robust GitHub Token Retrieval for Multi-Org Environments**: The logic for fetching GitHub tokens has been refined to better support scenarios where users might have multiple tokens or organizations. It now prioritizes main user tokens and includes a more comprehensive fallback mechanism.
*   **Idempotent Repository Sync State Updates with `org_id` Support**: The process for updating repository synchronization state is now idempotent, meaning repeated operations will yield the same result without unintended side effects. It also explicitly supports an `org_id`, improving multi-organization data management.

## 4. Breaking Changes

There are **no breaking changes** introduced in this release. All modifications are backward-compatible.

## 5. Technical Details

The following outlines the specific technical changes implemented:

*   **`src/core/commit_bus.py` - Commit Event Retry Logic**:
    *   The `CommitBusService` has been updated to increase the maximum number of retry attempts for `commit_events` from `3` to `5`. This enhances resilience to temporary network issues, API rate limits, or other transient problems. Events will now be retried more times before being considered permanently failed.

*   **`src/core/event_consumer.py` - GitHub Token Retrieval Enhancements**:
    1.  **Refactored `get_github_token` function**: The logic within `get_github_token` has been significantly revised. It now first attempts to retrieve the user's main GitHub token directly from the `users` table. If this primary lookup fails, it falls back to querying the `user_github_tokens` table, utilizing both the `user_id` and the provided `token_id`. This hierarchical lookup ensures more reliable token resolution, especially in multi-organization or complex user token setups.
    2.  **`_process_commit_event` passes `github_token_id`**: The `_process_commit_event` function now correctly extracts and passes the `github_token_id` from the incoming event payload to the `get_github_token` function. This crucial change enables the new fallback token retrieval logic to function as intended, ensuring the correct token is used for GitHub API interactions.
    3.  **`mark_repo_processed` Idempotent Upsert with `org_id`**: The `mark_repo_processed` function has been updated to accept an `org_id` parameter. The underlying database operation now uses an `INSERT ... ON CONFLICT (repo_id) DO UPDATE` (upsert) statement. This ensures that the `repo_sync_state` record is always correctly created if it doesn't exist, or updated if it does. This makes the operation idempotent and inherently supports multi-organization data management by allowing `org_id` to be stored with the sync state.
    4.  **Minor Code Cleanup**: Redundant lines related to `get_last_processed_sha` and `get_latest_commit_sha` were removed from `_process_commit_event`. These lines were not functionally relevant in their previous position and their removal streamlines the code.

## 6. Usage Examples

### Using the enhanced `mark_repo_processed` function

The `mark_repo_processed` function now requires an `org_id` and inherently provides idempotent updates to the `repo_sync_state` table.

**Old Usage (conceptual, as `org_id` was not directly supported):**
```python
# Assuming a function like this existed
# mark_repo_processed(repo_id="repo123", last_processed_sha="abcdef123", is_processed=True)
```

**New Usage:**
```python
from src.core.event_consumer import mark_repo_processed

repo_id = "repo-uuid-123"
org_id = "org-uuid-456" # New required parameter
last_processed_sha = "abcdef1234567890abcdef1234567890abcdef12"
is_processed = True
metadata = {"last_commit_date": "2023-10-27T10:00:00Z"} # Optional metadata

mark_repo_processed(
    repo_id=repo_id,
    org_id=org_id,
    last_processed_sha=last_processed_sha,
    is_processed=is_processed,
    metadata=metadata
)

# Calling it again with the same repo_id and org_id will update the existing record
# (e.g., if last_processed_sha changes) rather than creating a duplicate or failing.
mark_repo_processed(
    repo_id=repo_id,
    org_id=org_id,
    last_processed_sha="newsha_987654321098765432109876543210987654",
    is_processed=True,
    metadata={"last_commit_date": "2023-10-28T11:00:00Z", "status": "updated"}
)
```

### Leveraging enhanced `get_github_token` (Implicit)

The `get_github_token` function's improved logic is primarily an internal reliability enhancement. Developers typically interact with it indirectly through the event processing flow. When a `commit_event` includes a `github_token_id`, the system will now more robustly attempt to resolve the correct token:

```python
# This is an example of an event structure that will benefit
# from the new token retrieval logic in _process_commit_event.
event_payload = {
    "type": "commit_event",
    "user_id": "user-uuid-789",
    "github_token_id": "token-uuid-abc", # This ID is now properly used for fallback
    "repo_id": "repo-uuid-123",
    # ... other event data
}

# In _process_commit_event, this token will be resolved:
# token = get_github_token(user_id=event_payload["user_id"], token_id=event_payload["github_token_id"])
```

### Event Retry Mechanism (Internal)

The increased retry attempts for commit events are an internal configuration change. There's no direct code usage example for this, but its benefit is observed in higher resilience:

*   **Before**: An event might fail permanently after 3 transient errors.
*   **After**: The same event will now attempt up to 5 retries, significantly increasing its chance of successful processing once the transient issue resolves.

## 7. Testing

To verify the correct functioning of these changes, the following testing scenarios are recommended:

*   **Event Processing Reliability**:
    *   **Simulate Transient Failures**: Introduce temporary network errors, GitHub API rate limits, or transient database connection issues during event processing. Observe if events that would previously fail after 3 attempts now succeed after 4 or 5 attempts (if the transient issue resolves).
    *   **Monitor Failed Event Metrics**: Ensure that the rate of permanently failed events decreases, indicating improved resilience.

*   **GitHub Token Retrieval (Multi-Org Scenarios)**:
    *   **Scenario 1: Main User Token Exists**: Test with a user who has a direct `github_token` entry in the `users` table. Verify that `get_github_token` successfully retrieves this token when `github_token_id` is provided in the event.
    *   **Scenario 2: Fallback Token Exists**: Test with a user where the `github_token` in `users` is `NULL` or invalid, but a valid token exists in `user_github_tokens` with the matching `user_id` and `token_id`. Verify the fallback mechanism correctly retrieves this token.
    *   **Scenario 3: Multi-Organization Context**: Create a user associated with multiple GitHub tokens (e.g., via `user_github_tokens` for different organizations). Ensure that when an event specifies a `github_token_id`, the correct token for that specific context is retrieved.
    *   **Scenario 4: Invalid/Missing Token ID**: Test events with an invalid or missing `github_token_id`. Ensure appropriate error handling (e.g., logging, event failure) occurs.

*   **Repository Sync State Updates (`mark_repo_processed` with `org_id` and Upsert)**:
    *   **Initial Creation**:
        *   Call `mark_repo_processed` for a new `repo_id` and `org_id`. Verify that a new record is created in the `repo_sync_state` table with the correct `repo_id`, `org_id`, `last_processed_sha`, and other fields.
    *   **Idempotent Update**:
        *   Call `mark_repo_processed` again for the *same* `repo_id` and `org_id`, but with a *different* `last_processed_sha` or `metadata`. Verify that the existing record is *updated* and no new record is created.
        *   Verify that `org_id` in the database is correctly persisted for these records.
    *   **Multiple Organizations for Same Repository (if applicable to data model)**: If a single `repo_id` can conceptually exist under different `org_id`s (e.g., if a repo is forked), test that separate `repo_sync_state` entries are correctly created for each `org_id` and `repo_id` combination. (Note: The current schema implies `repo_id` as unique key, so this might not be a direct test case unless `repo_id` is globally unique and `org_id` is just an attribute). Assuming `repo_id` is unique and `org_id` is an attribute, then `(repo_id, org_id)` is not a compound key for the upsert, only `repo_id` is. *Self-correction: The `technical_details` explicitly states `ON CONFLICT (repo_id) DO UPDATE`, implying `repo_id` is the primary key for the upsert, not `(repo_id, org_id)`. Therefore, testing multiple organizations for the *same* `repo_id` would result in the `org_id` being updated, not creating a new record.* So, the test would be: Ensure `org_id` is updated correctly when the `repo_id` exists.
