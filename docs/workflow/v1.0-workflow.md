The Lekhak AI system is an AI-powered documentation platform that automatically analyzes codebases and generates comprehensive, hierarchical documentation. Its architecture is event-driven, leveraging GitHub webhooks for continuous code analysis and AI assistance to enrich documentation.

## Workflow and Process Documentation

This document outlines the key workflows and processes involved in the development, deployment, testing, and release of Lekhak AI.

---

### 1. Development Workflow

The development workflow for Lekhak AI involves managing both a Python-based backend service and a Next.js/TypeScript frontend application.

1.  **Environment Setup:**
    *   **Clone Repository:** Developers begin by cloning the `AuditorEnvelope/lekhak_ai` repository.
    *   **Backend Dependencies:** Install Python dependencies using `pip`:
        ```bash
        pip install -r requirements.txt
        ```
    *   **Frontend Dependencies (Pustak):** Navigate to the `pustak/` directory and install Node.js dependencies:
        ```bash
        cd pustak/
        npm install # or yarn install
        cd ..
        ```
    *   **Environment Variables:** Configure essential API keys and database connections:
        ```bash
        export GITHUB_TOKEN="ghp_your_token"
        export GEMINI_API_KEY="your_gemini_key"
        export DATABASE_URL="postgresql://localhost/lekhak_ai" # If using external DB
        # Additional environment variables for Stripe, etc., would also be set.
        ```
    *   **Database (Optional for local development, recommended for full functionality):**
        ```bash
        createdb lekhak_ai
        psql lekhak_ai < schema.sql
        ```
        Database migrations (`migrate_add_installation_id.py`) are applied as needed for schema updates.

2.  **Local Development:**
    *   **Backend Server:** Start the main Python server:
        ```bash
        python src/main.py
        ```
        This server will run the `Event Consumer` and `Smart Processor` components.
    *   **Frontend Server:** In a separate terminal, start the Next.js development server from the `pustak/` directory:
        ```bash
        cd pustak/
        npm run dev # or yarn dev
        ```
    *   **Code Changes:** Developers write code in Python (`src/`) for the backend logic (core services, utilities, integrations) and TypeScript/React (`pustak/src/`) for the user interface and frontend API routes.
    *   **Version Control:** All code changes are managed using Git, with feature branches, pull requests, and code reviews being standard practice.

### 4. CI/CD Pipeline

The Lekhak AI system is designed with a robust CI/CD pipeline to automate the integration, testing, and deployment of code changes.

1.  **Continuous Integration (CI):**
    *   **Trigger:** The CI pipeline is initiated automatically on every push to a branch and for every pull request (PR) created against the main branches (e.g., `main`, `develop`).
    *   **Steps:**
        *   **Checkout Code:** The latest code is fetched from the Git repository.
        *   **Dependency Installation:**
            *   Backend: `pip install -r requirements.txt`.
            *   Frontend: `npm install` (or `yarn install`) in `pustak/`.
        *   **Linting & Formatting:** Code linting and formatting checks are executed for both Python and TypeScript codebases.
        *   **Testing:** All automated unit and integration tests are run for both backend and frontend components.
        *   **Build Artifacts:** Successful CI runs result in the building of Docker images for the backend and frontend components.

2.  **Continuous Deployment (CD):**
    *   **Trigger:** After a successful CI run on a designated branch (e.g., `main`), or upon merging a PR into `main`, the CD pipeline is triggered. Alternatively, releases can be triggered by version tags.
    *   **Steps:**
        *   **Docker Image Push:** Built Docker images are tagged with a unique identifier (e.g., commit hash, version number) and pushed to a container registry (e.g., Docker Hub, AWS ECR).
        *   **Database Migrations:** Any pending database schema migrations (`.sql` files or migration scripts) are applied to the target database environment.
        *   **Deployment to Environment:** The updated Docker images are deployed to a staging or production environment. This typically involves updating the running containers (e.g., `docker-compose up -d`, or orchestrated deployment via Kubernetes, ECS, etc.).
        *   **Environment Variables:** Production environment variables are securely injected into the deployed containers.
        *   **Health Checks:** Post-deployment, automated health checks verify the availability and functionality of the deployed services.

### 5. Release Process

Lekhak AI's release process adheres to semantic versioning and incorporates change tracking to manage updates effectively.

1.  **Semantic Versioning:**
    *   The `README` explicitly states "Version Management - Semantic versioning with change tracking." This means releases follow a `MAJOR.MINOR.PATCH` format (e.g., `v1.0.0`).
    *   **PATCH:** For backward-compatible bug fixes.
    *   **MINOR:** For backward-compatible new features.
    *   **MAJOR:** For backward-incompatible changes.

2.  **Release Planning:**
    *   Features and bug fixes intended for a specific release are grouped, typically in a dedicated release branch or marked through project management tools.

3.  **Pre-Release Activities:**
    *   **Code Freeze:** A period where no new features are merged into the release branch, focusing solely on bug fixes.
    *   **Final Testing:** Extensive testing, including end-to-end and user acceptance testing (UAT), is performed.
    *   **Documentation Updates:** User-facing and internal documentation are updated to reflect new features or changes.

4.  **Version Bumping:**
    *   Before a release, the version number is updated in relevant configuration files (e.g., `pyproject.toml` for Python, `package.json` for Next.js).
    *   A `CHANGELOG.md` file is typically updated to summarize changes since the last release.

5.  **Tagging and Publishing:**
    *   The release commit is tagged with the semantic version (e.g., `git tag v1.2.3`).
    *   This tag is pushed to the remote repository (`git push --tags`).
    *   The CD pipeline is often configured to trigger a production deployment specifically when a new version tag is pushed.

6.  **Post-Release Monitoring and Support:**
    *   After deployment, the system is closely monitored for performance, errors, and any regressions.
    *   Feedback from users is collected and addressed in subsequent releases.
    *   Rollback procedures are in place to revert to a previous stable version if critical issues are identified.
